Sanitized Sample Technical Report ("1-of-N" Demo)

Below is a complete, sanitized sample report (ExampleVault.sol) illustrating the exact structure, execution trace depth, refuted-candidate filtering, and patch verification delivered to clients.

1. Finding Passport

Repository / Commit example-defi-protocol / commit a1b2c3d (branch: main)
Component / Function contracts/vault/ExampleVault.sol — claimAndCompound(uint256 amount, uint256 minShares)
Defect Class Reward Debt Accounting Desynchronization
Severity Medium (no direct theft of principal deposits, but every partial compound permanently erases the user's uncompounded pending reward balance, locking those reward tokens inside the vault contract)
Verification Status Confirmed via local execution harness (Foundry); mainnet and public testnets were NOT touched.

2. Summary & Root Cause

The claimAndCompound function explicitly allows a user to reinvest a partial amount of their accrued rewards (amount <= pending) into newly minted vault shares. However, at the end of the function, user.rewardDebt is reset based on the user's full updated share balance as if the entire pending reward had been claimed or compounded. Consequently, the uncompounded remainder (pending - amount) is silently wiped from the user's claimable balance and permanently orphaned inside the contract.

Sanitized code snippet (contracts/vault/ExampleVault.sol, lines 142–153):

function claimAndCompound(uint256 amount, uint256 minShares) external nonReentrant returns (uint256 minted) {
    UserInfo storage user = userInfo[msg.sender];
    uint256 pending = (user.shares * accRewardPerShare) / 1e18 - user.rewardDebt;
    require(amount <= pending, "ExampleVault: exceeds pending");

    minted = _convertToShares(amount);
    require(minted >= minShares, "ExampleVault: slippage");
    totalShares += minted;
    user.shares += minted;
    user.rewardDebt = (user.shares * accRewardPerShare) / 1e18; // <-- BUG: overwrites full debt, erasing (pending - amount)
}

3. Reproducible PoC & Execution Trace

Local test execution command:
forge test --match-test test_ClaimAndCompound_PartialErasesUnclaimedRewards -vvv

  • Initial vault state: totalAssets = 100_000e18, totalShares = 100_000e18, reward index accRewardPerShare = 0.05e18 (50_000_000_000_000_000).
  • Actor Alice position: user.shares = 10_000e18, user.rewardDebt = 0. Accrued claimable reward pending = 500e18.
  • Alice executes: vault.claimAndCompound(200e18, 200e18) (compounding 200 out of 500 accrued reward tokens).
  • Target invariant: claimable_before == compounded_amount + claimable_after (500e18 == 200e18 + 300e18).
  • BEFORE execution: user.shares = 10_000.000000e18, user.rewardDebt = 0.000000e18, claimable_before (pending) = 500.000000e18.
  • AFTER calling claimAndCompound(200e18, 200e18): minted = 200.000000e18, user.shares = 10_200.000000e18, user.rewardDebt = (10_200e18 * 0.05e18) / 1e18 = 510.000000e18, claimable_after = 0.000000e18.
  • Measured discrepancy: 300.000000e18 reward tokens (60% of Alice's accrued yield) are permanently lost to the user in a single valid partial-compound transaction.

4. Candidates Refuted by Execution (Noise Filtered Out for Your Team)

Standard static analyzers flag several locations in this contract that look alarming on paper. We tested each candidate via actual execution and proved them safe so your engineers waste zero time triaging false positives:

  • Refuted Candidate A (ExampleVault.sol:98, rounding direction in _convertToShares on initial deposit): Static scanners flag a potential first-depositor inflation/donation attack resulting in zero-share mints. Execution testing against the constructor's virtual offset initialization (VIRTUAL_SHARES = 1e6 and VIRTUAL_ASSETS = 1e6 at line 44) proved that for any user deposit >= 1000 wei, an attacker donating up to 10_000e18 tokens suffers an immediate >99.99% capital loss. Verdict: SAFE (Refuted by execution).
  • Refuted Candidate B (ExampleVault.sol:211, state update ordering in emergencyWithdraw): Static scanners flag asset.safeTransfer(msg.sender, assets) occurring prior to the lastHarvestBlock update as a reentrancy hazard. Execution testing with a malicious ERC-777 callback token confirmed that the function is guarded by nonReentrant and zeroes user.shares at line 206 before the external call; a stale lastHarvestBlock within the same transaction cannot be leveraged to extract extra funds or shares. Verdict: SAFE (Refuted by execution).

5. Fix Recommendation & Post-Fix Verification

Deduct the uncompounded reward remainder (unpaid = pending - amount) from the newly calculated reward debt baseline (since user.shares increased, newBaseline = (user.shares * accRewardPerShare) / 1e18 is guaranteed to be strictly greater than pending and unpaid, preventing underflow): 

     totalShares += minted;
     user.shares += minted;
-    user.rewardDebt = (user.shares * accRewardPerShare) / 1e18;
+    uint256 unpaid = pending - amount;
+    uint256 newBaseline = (user.shares * accRewardPerShare) / 1e18;
+    user.rewardDebt = newBaseline - unpaid;
 }

Post-fix test execution result: forge test --match-test test_ClaimAndCompound_PartialErasesUnclaimedRewards -vvv — PASS. After calling claimAndCompound(200e18, 200e18), user.rewardDebt updates to 210.000000e18, leaving claimable_after = 300.000000e18. The accounting invariant claimable_before == compounded_amount + claimable_after holds across 10,000 fuzz runs.

Sample Report #2 — Publicly Verifiable Rust / WebAssembly Case (wasm-bindgen Issues #5459, #5460 & Fix PR #5461)

While security vulnerabilities remain strictly under embargo (or permanent confidentiality at the maintainer's request), non-security robustness defects can be shared openly. Below is a live, publicly verifiable Rust/WASM case found by Sir Revizor in wasm-bindgen/wasm-bindgen:

Public Upstream Links Issue #5459 (descriptor panic) · Issue #5460 (truncated section panic) · Community Fix PR #5461
Component / Location crates/cli-support/src/descriptor.rs:345 and crates/cli-support/src/wit/mod.rs:2989
Defect Class Unhandled Boundary Value & Truncated Section Causing Host Process Panic (Exit Code 101 instead of Result::Err)
Verification Status Confirmed by execution with a minimal 11-byte WASM binary reproducer; control cases return expected Err.

Root Cause & Code Snippet: When decoding the u32 type-descriptor stream emitted by a WASM guest export (__wbindgen_describe_*), an unknown descriptor tag hits an unconditional panic!("unknown descriptor: {other}") arm instead of returning a recoverable Result::Err (and similarly get_remaining(...).unwrap() panics on a truncated __wasm_bindgen_unstable section):

// crates/cli-support/src/descriptor.rs:345
other => panic!("unknown descriptor: {other}"), // <-- crashes process (exit 101) instead of returning Err

Execution Proof & Fix Verification: Passing a minimal 11-byte WASM module pushing 0xFFFFFFFF aborts the CLI with thread 'main' panicked at crates/cli-support/src/descriptor.rs:345:22: unknown descriptor: 4294967295 (exit code 101). Replacing unconditional panics with bail!("unknown descriptor value: {other}") (PR #5461) restores graceful error handling.

Coordinated Disclosure Portfolio & Pre-Embargo Anonymization Rule

Public Disclosure Board: github.com/ais-space/disclosures →

All proactive research and pre-qualification of prospective leads is performed exclusively on public open-source GitHub repositories in a local isolated environment under strict Coordinated Vulnerability Disclosure (CVD) rules — never interacting with live production deployments or unauthorized private code. Any critical defect putting live user funds at immediate risk is reported to the project maintainer immediately and free of charge with zero commercial conditions.

Why Active Cases Are Numbered (Case #001, Case #002, ...): Because even revealing that an unpatched vulnerability exists in a named project can alert attackers before a patch is released, we never publish a project's name while an embargo is running. On our public board (github.com/ais-space/disclosures), pending evaluations are tracked strictly by sequential number and technology domain (e.g., Case #001 — Rust/WASM Plug-in Runtime SDK, Case #002 — Rust/WASM Host Library, Case #003 — Solidity Smart-Contract Library).

Once an embargo period concludes, each numbered case resolves to one of two permanent records:

  • Public Resolution (with vendor patch): "Case #NNN is project [Name]; vulnerability [Class] was identified and fixed" — with links to the upstream patch and full reproduction report.
  • Confidential Resolution (at maintainer's request): "Case #NNN — Despite expiration of the embargo period, at the maintainer's request we do not disclose the project name or technical details, respecting their right to confidentiality."
  • Commercial Monitoring Subscribers: For paying monitoring clients, all findings are governed by mutual NDA and are never published on the disclosure board.
